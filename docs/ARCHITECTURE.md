# 빈티지 디카 작례 사이트 — 기술 스택·아키텍처

> 상태: 초안 · 작성일: 2026-11-12 · 관련 문서: [PRD.md](./PRD.md)

## 1. 기술 스택

| 영역 | 선택 | 고른 이유 |
|---|---|---|
| 프론트엔드 | **Next.js + TypeScript + Tailwind CSS** | 기종 페이지가 네이버·구글 검색에 걸려야 함. 서버 렌더링으로 검색봇이 내용을 읽을 수 있음 |
| 화면 대응 | **반응형 웹 하나로** (모바일 우선) | 휴대폰용·데스크톱용을 따로 만들지 않음. 상세는 2.1 |
| 프론트 배포 | **Vercel** | Next.js 공식 호스팅. 무료 플랜은 비상업용인데 MVP는 광고 없이 운영하므로 문제없음 |
| 백엔드 | **Spring Boot + JPA** | |
| DB | **PostgreSQL** (Lightsail 관리형) | 자동 백업·복구. 나중에 색감 벡터 검색을 붙일 때 pgvector 확장을 쓸 수 있음 |
| 로그인 | **구글, 카카오** (Spring Security OAuth2 Client) | 카카오는 provider 설정을 직접 추가해야 함 |
| 로그인 유지 | **세션 쿠키** (Spring Session JDBC) | 탈퇴·권한 회수가 즉시 반영됨. 상세는 [API.md](./API.md) 1.2 |
| 이미지 저장소 | **Cloudflare R2** | S3 호환이라 AWS SDK 그대로 사용. 전송(다운로드) 비용 무료, 10GB 무료 |
| 개발용 저장소 | **로컬 폴더** (`app.storage.type=local`, `backend/data/images`) | `ImageStorage` 인터페이스로 R2와 바꿔 끼운다. local 프로필에서만 공개 폴더를 `/dev-images/**`로 보여준다. R2 구현은 배포 전에 추가 |
| 썸네일·보기용 이미지 | **업로드 시 서버에서 생성** (Thumbnailator 등). 썸네일 640px, 보기용 1600px | 추가 비용 없음. GPS 삭제와 같은 시점에 처리 (3.1) |
| 이미지 주소 | **`img.{도메인}`** (R2 공개 버킷에 커스텀 도메인 연결) | R2 기본 주소(`r2.dev`)는 개발용이라 속도 제한이 있음. 커스텀 도메인이어야 Cloudflare 캐시를 씀 |
| 백엔드 배포 | **AWS Lightsail 2GB + Docker** | 배치가 서버 안에서 돌아서 항상 켜진 서버가 필요. 고정 요금 |
| 관리자 | **화면 없이 ADMIN API + Swagger UI** | MVP 처리량에는 충분. 많아지면 화면 추가 |

## 2. 시스템 구성

```
                 ┌────────────────────┐
  브라우저 ──────▶│ Next.js (Vercel)   │
     │           │ 서버 렌더링         │
     │           └─────────┬──────────┘
     │                     │ REST API
     │                     ▼
     │           ┌────────────────────┐        ┌──────────────────┐
     │           │ Spring Boot API    │───────▶│ PostgreSQL       │
     │           │ (Lightsail+Docker) │        │ (Lightsail 관리형) │
     │           │ - 인증 (OAuth2)     │        └──────────────────┘
     │           │ - 업로드·EXIF 처리   │
     │           │ - 검색·조회          │        ┌──────────────────┐
     │           │ - 배치 (스케줄러)     │───────▶│ Cloudflare R2    │
     │           └─────────┬──────────┘ 저장    │ 공개: 썸네일·보기용 │
     │                     │                    └────────┬─────────┘
     │                     │ 배치 호출                     │
     │                     ▼                             │
     │           ┌──────────────────────┐                │
     │           │ Wikimedia Commons API │                │
     │           └──────────────────────┘                │
     │                                                   │
     └──────── 모든 작례 이미지 (업로드·Commons 모두 R2에서) ──┘
```

- 이미지는 API 서버를 거치지 않고 브라우저가 **R2 공개 주소(`img.{도메인}`)** 에서 직접 받는다. 사용자 업로드와 Commons 작례 모두 R2에 저장하므로 외부 이미지 주소를 쓰지 않는다. 원본은 비공개 버킷에 있어 브라우저가 받을 수 없다.
- 배치는 MVP에서는 Spring의 `@Scheduled`로 API 서버 안에서 돌린다. 분리 기준은 3.7 참고.

### 2.1 화면 대응 (반응형 웹)

휴대폰용과 데스크톱용 프론트를 따로 만들지 않는다. **같은 페이지, 같은 코드**에서 화면 폭에 따라 배치만 바뀌게 만든다.

- **모바일 우선**: 휴대폰 화면을 먼저 만들고 넓은 화면용 배치를 덧붙인다. 사용자가 주로 인스타에서 휴대폰으로 들어오기 때문이다. 와이어프레임도 휴대폰 기준이다.
- **구현**: Tailwind CSS의 화면 폭 접두사로 처리한다.

```html
<!-- 기본 3칸, 768px 이상 4칸, 1024px 이상 6칸 -->
<div class="grid grid-cols-3 md:grid-cols-4 lg:grid-cols-6">
```

| 기준 | 화면 폭 | 대상 |
|---|---|---|
| 기본 | 768px 미만 | 휴대폰 |
| `md` | 768px 이상 | 태블릿 |
| `lg` | 1024px 이상 | 데스크톱 |

화면별로 달라지는 부분:

| 화면 | 휴대폰 | 데스크톱 |
|---|---|---|
| 작례 격자 (기종 페이지, 프로필) | 3칸 | 5~6칸 |
| 작례 상세 | 사진 위, 촬영 정보 아래 | 사진 왼쪽, 촬영 정보 오른쪽 |
| 로그인·신고·탈퇴 확인 창 | 아래에서 올라오는 시트 | 화면 가운데 팝업 |
| 상단 메뉴 | 아이콘 위주로 간단히 | 검색창까지 상단에 펼침 |
| 브랜드 페이지 기종 목록 | 2칸 | 4칸 |

- 페이지당 작례 수(24장)는 화면 크기와 관계없이 같다. 24는 3, 4, 6으로 모두 나누어떨어져서 마지막 줄이 비지 않는다.
- 나중에 iOS·안드로이드 앱을 만들게 되면 앱은 따로 개발한다. 백엔드 API는 그대로 쓴다.

## 3. 주요 흐름

### 3.1 작례 업로드

1. 사용자가 원본 사진을 고른다.
2. 서버가 EXIF를 읽는다. (예: metadata-extractor 라이브러리)
   - EXIF가 없으면 거부하고 원본 파일 안내를 보여준다.
3. EXIF의 제조사와 모델명으로 기종을 찾는다. (`camera_alias` 테이블에서 정규화된 문자열로 매칭)
   - 찾으면 → 기종 확정
   - 못 찾으면 → **미분류** 상태
4. 인식 결과를 사용자에게 보여주고 확인을 받는다.
5. 저장: 한 장을 세 가지로 만들어 R2에 올린다.

   | 종류 | 크기 | 용도 | 저장 위치 |
   |---|---|---|---|
   | 썸네일 | 긴 변 640px | 격자 | **공개** 버킷 (`img.{도메인}`) |
   | 보기용 | 긴 변 1600px | 작례 상세 화면 | **공개** 버킷 (`img.{도메인}`) |
   | 원본 | 그대로 (GPS만 삭제) | 화면에 쓰지 않음. 나중에 크기를 다시 만들거나 색감 분석 기능에 사용 | **비공개** 버킷 (외부 접근 불가) |

   - 썸네일과 보기용은 EXIF를 전부 지운 파일로 만든다. 촬영 정보는 DB에서 읽어 화면에 따로 보여준다.
   - 원본은 GPS 태그만 지우고 나머지 EXIF는 남긴다.
   - 썸네일 640px인 이유: 모바일 3열 격자 한 칸이 고해상도 화면에서 실제로 약 400px가 필요하다. 여유를 두었다.
   - 보기용 1600px인 이유: 상세 화면에서 카메라의 색감과 느낌을 보기에 충분하고, 2~5MB 원본보다 훨씬 빨리 뜬다.
6. 플래시 여부, 촬영일, 노출 정보, EXIF 원문 모델명은 DB에 저장한다.

> GPS는 원본 파일에서도 지운다. 원본은 비공개지만 개인정보는 애초에 남기지 않는다.

**다운로드 기능은 두지 않는다.**
- 다운로드 버튼이나 "원본 보기"는 만들지 않는다.
- 원본은 비공개 버킷에 있어서 주소를 알아도 받을 수 없다.
- 단, 화면에 보이는 사진(보기용 1600px)은 브라우저 특성상 우클릭 저장이나 캡처를 완전히 막을 수 없다. 우클릭 막기 같은 장치는 효과가 약하고 사용성만 나빠져서 쓰지 않는다. 남의 사진 무단 사용은 이용약관과 신고로 대응한다.

### 3.2 미분류 작례 연결 (관리자)

1. 관리자 화면에서 미분류 EXIF 모델명 목록을 본다. (모델명별 작례 수 포함)
2. 새 기종을 만들거나 기존 기종을 고른다.
3. 그 EXIF 모델명을 `camera_alias`에 추가한다.
4. 같은 모델명의 미분류 작례가 전부 해당 기종으로 바뀐다.

MVP에서는 관리자 화면 없이 ADMIN 권한 API를 Swagger UI에서 호출한다.

### 3.3 Commons 수집 배치

> Flickr 대신 Wikimedia Commons를 쓴다. Flickr는 무료 계정의 API 키 발급을 막아 두어 Pro 구독이 필요하다. (2026-11-17 확인)

**기종과 Commons 분류 연결**
- Commons는 기종별로 "Category:Taken with ○○" 분류가 있다. 기종마다 어떤 분류에서 가져올지 `camera_source_category`에 적어 둔다.
- 분류 이름은 해외 모델명 기준이다. 한 기종에 분류가 여러 개일 수 있다.
  - 예) IXUS 30 → "Taken with Canon Digital IXUS 30" (미국 이름 PowerShot SD200 사진도 이 분류에 함께 있음)
  - 예) VLUU NV3 → "Taken with Samsung NV3"
  - 캐논 IXY(일본 이름), 삼성 케녹스·블루(국내 이름)로는 거의 나오지 않는다.

**수집 순서**
1. 분류의 파일 목록과 정보를 한 번에 받는다. (`generator=categorymembers` + `prop=imageinfo`, 요청당 최대 50장)
   - 받는 정보: 파일 주소, 크기, EXIF(제조사·모델·플래시·촬영일 등), 작가, 라이선스 이름·링크
2. 걸러 낸다.
   - EXIF 카메라 모델이 해당 기종과 맞지 않으면 버린다. (`camera_exif_model`로 확인)
   - **허용 라이선스가 아니면 버린다.** 허용: 퍼블릭 도메인, CC0, CC BY, CC BY-SA (버전 무관)
   - 작가 정보나 라이선스 정보가 없으면 버린다.
   - JPEG가 아니면 버린다.
   - 긴 변이 **400px 미만**이면 버린다. 휴대폰 3칸 격자 한 칸에 고화질 화면 기준 약 400px가 필요해서, 그보다 작으면 썸네일도 흐리다. (Commons처럼 최소 크기는 낮게 두고, 줄인 사진은 표시만 한다)
   - 그보다 큰 사진은 작게 줄인 사진이라도 가져온다. 대신 **원본 크기 여부를 판별**해서 `photo.is_original_size`에 저장한다. (아래 "원본 크기 판별")
2-1. **고르게 고른다.** 조건을 통과한 사진을 작가별로 묶고, **작가별로 돌아가며 한 장씩, 작가당 최대 10장**까지 골라 기종당 최대 100장을 채운다.
   - 파일 이름 순으로 앞에서부터 가져오면 한 작가 사진이 몰린다. (PoC에서 처음 100장 중 상당수가 한 작가 사진이었음)
   - 한 사람 사진이 몰리면 카메라가 아니라 그 사람의 설정·습관·찍는 장소가 카메라 특성처럼 보이고, 그 작가가 삭제를 요청하면 페이지가 한 번에 비게 된다.
   - 후보는 분류에서 최대 500장까지 받아 보고 고른다.
3. 남은 사진을 받아서 썸네일(640px)과 보기용(1600px)을 만들어 R2 공개 버킷에 저장한다.
   - Commons가 제공하는 축소본 중 1600px 이상인 크기를 받아서 우리 규격으로 다시 만든다. 원본 전체를 받지 않아 전송량을 줄인다.
   - 공개 파일의 EXIF는 사용자 업로드와 똑같이 모두 지운다.
   - **원본은 저장하지 않는다.** 필요하면 Commons에서 다시 받는다.
4. `photo`(source = COMMONS)와 `commons_meta`를 저장한다.

**원본 크기 판별** (사용자 업로드와 Commons 작례 모두)
- 기종마다 카메라의 원래 해상도(`camera.native_width`, `native_height`)를 기종 정보로 넣어 둔다. (예: DSC-T1 2592×1944)
- 사진의 긴 변이 기종 원래 해상도 긴 변의 **95% 이상**이면 원본 크기(`is_original_size = true`). 살짝 잘라 낸 사진까지 허용하기 위해 95%로 둔다.
- 기종의 원래 해상도를 모르면 `null`로 두고, 원본 크기 필터를 켜면 빠진다.
- 미분류 작례는 기종이 정해질 때(관리자 연결 시) 판별한다.
- 상세 화면에서 1600px보다 작은 사진은 늘리지 않는다. 보기용 파일도 원래 크기 그대로 만든다.

**PoC 결과 (2026-11-17, `poc/commons_poc.py`)**: 분류 6개 확인. 라이선스·작가·EXIF 조건은 96~99% 통과. 긴 변 1024px 기준을 넣었을 때 사진이 많은 분류(DSC-T1, FinePix Z1, IXUS 30)는 작가 88~100명에게서 100장을 채웠고, 사진이 적은 분류(Coolpix S1, Samsung NV3, Exilim EX-FH20)는 작가 10~24명에게서 33~59장이 나왔다. (이후 작은 사진도 포함하고 원본 크기 필터로 거르기로 바꿔서, 실제로는 이보다 많아진다.) 출시 전 목표(기종당 20장)는 모두 넘는다. 사진은 대부분 거리·건물 같은 기록용 사진이라, 인물·실내·플래시 같은 "디카 감성" 작례는 사용자 업로드로 채워야 한다.

**기종당 최대 장수**: 처음에는 기종당 최대 100장. 저장 공간을 아끼고, 출시 전에 관리자가 훑어보고 작례로 쓰기 애매한 사진(제품 사진, 문서 스캔 등)을 지울 수 있는 양으로 둔다.

**요청 예절과 속도** (기종을 크게 늘릴 계획이라 처음부터 적용)

Commons는 API 키가 없는 대신 위키미디어의 이용 규칙을 지켜야 한다. 어기면 요청이 막힌다. (2026-11-17 조사 중 연속 요청으로 실제로 막힌 적 있음)

- **User-Agent에 서비스 이름과 연락처**를 넣는다. 현재: `dica-jakrye/0.1 (dicajakrye@gmail.com) java-http-client/21` (운영 메일. 도메인이 생기면 서비스 주소 추가)
  - 연락처 없이 보냈을 때는 3초 간격에서도 10장 남짓 받으면 429와 "10분 뒤에 오라"(Retry-After 600초)로 막혔다. 연락처를 넣은 뒤에는 같은 조건에서 막히지 않았다. (2026-11-17)
- **한 번에 하나씩 순서대로** 요청한다. 동시에 여러 요청을 보내지 않는다.
- API 요청에 `maxlag=5`를 붙인다. 위키미디어 서버가 바쁘면 거절되고, 그때는 잠시 쉬었다 다시 보낸다.
- 이미지 파일 다운로드는 **3초에 1장 이하**로 한다. (1초 간격에서 429로 막힘. 처음 요청하는 축소본은 서버가 새로 만들어야 해서 부담이 크다)
- 축소본은 1600px를 요청하지만 Commons가 표준 크기(1920px)로 바꿔서 준다. 받은 뒤 우리가 1600px로 줄인다.
- 429면 Retry-After를 따른다. 2분 넘게 기다리라고 하면 기다리지 않고 이번 실행을 끝내고 다음 실행에서 이어 간다. (이미 받은 사진은 남아 있음)
- 막히면(응답 오류, 429 등) 대기 시간을 늘려 가며 다시 시도하고, 계속 실패하면 그 기종은 다음 실행으로 미룬다.

이렇게 하면 수집 속도는 서버 성능이 아니라 **다운로드 속도 제한**이 결정한다.

예) 기종 500개 × 100장 = 50,000장 → 3초에 1장이면 약 42시간. 하루 50개 기종씩 나눠 돌리면 10일 남짓

- **나눠서 수집**: 하루에 모든 기종을 돌지 않는다. `camera.commons_collected_at`이 오래된 기종부터 하루 N개씩 돈다. (초기값 50개, 운영하며 조정)
- **새 것만 수집**: 분류에 들어온 시각 순으로 정렬해서 지난 수집 이후에 추가된 파일만 확인한다. 처음 수집하는 기종만 전체를 본다.
- **중단돼도 이어서**: 기종 하나를 끝낼 때마다 `commons_collected_at`을 갱신해서, 배치가 중간에 끊겨도 다음 실행 때 남은 기종부터 이어 간다.
- **이미 가져온 파일은 건너뛴다**: `commons_meta.commons_page_id`로 확인한다.

**알려진 한계 (2026-11-17 실제 수집에서 확인)**
- 같은 작가가 Commons에 여러 표기로 올라와 있다. 예) "Klaus Nahr", "Klaus Nahr from Germany", "KlausNahr", "https://www.flickr.com/people/klausnahr/". 지금은 글자가 다르면 다른 작가로 세서 **작가당 10장 제한이 느슨해질 수 있다.** 실제 수집에서 한 기종에 같은 사람이 4가지 표기로 섞인 경우가 있었다.
- 작가 칸이 사람 이름이 아니라 Flickr 주소인 경우가 있다. 화면에는 그대로 보여 주되, 정리 방법(주소면 "Flickr 사용자"로 표시 등)은 프론트를 만들 때 정한다.

### 3.4 Commons 정리 배치

- 일주일에 한 번, 저장된 Commons 작례가 Commons에 아직 있는지 확인한다. (페이지 ID로 요청당 50개씩)
- Commons에서 삭제된 파일(저작권 문제 등으로 지워진 것)은 우리 쪽 작례도 지우고 R2 파일도 지운다.
- 저작권자가 우리에게 직접 삭제를 요청하면 관리자 API로 바로 지운다.

### 3.5 인기 기종 배치 — MVP에서 제외

인기 기종 기능은 추후로 뺐다. 네이버 데이터랩 검증에서 기종 단위 검색량이 너무 적게 나왔기 때문이다. 조사한 API 정보, 처리 설계, 검증 결과는 [LATER.md](./LATER.md)에 보관한다.

### 3.6 신고 처리

1. 로그인한 사용자가 작례 상세에서 신고 사유를 골라 신고한다.
2. 같은 사용자가 같은 작례를 중복 신고할 수 없다.
3. 관리자가 ADMIN API로 신고 목록(미처리 우선)을 본다.
4. 삭제하면 DB에서 작례를 지우고 R2의 썸네일·보기용·원본 파일을 모두 지운다. (Commons 작례는 원본이 없으므로 썸네일·보기용만)
5. 기각하면 신고 상태만 바꾼다.

### 3.7 배치 실행 구조와 분리 기준

MVP는 배치를 API 서버 안에서 돌린다. 배치는 대부분 외부 API 응답을 기다리는 작업이고, 수집 속도는 서버가 아니라 Commons 다운로드 속도 제한이 결정하기 때문이다. 단 Commons 사진의 썸네일·보기용을 만드는 작업은 메모리를 쓰므로, 업로드 처리와 합쳐 동시에 처리하는 이미지 수를 제한한다. 대신 나중에 쉽게 떼어 낼 수 있게 처음부터 아래처럼 만든다.

- **코드 분리**: 배치 코드는 `batch` 패키지에 모으고 웹 요청 코드(컨트롤러)에 의존하지 않는다. 공통 로직은 서비스 계층을 함께 쓴다.
- **스레드 분리**: 배치 전용 스케줄러 스레드 풀을 따로 둬서 사용자 요청 처리와 섞이지 않게 한다.
- **실행 시간**: 사용자가 적은 새벽 시간대에 돌린다.
- **실행 기록**: 배치마다 시작·종료 시각, 처리 건수, 실패 건수를 로그로 남긴다. 분리 시점을 판단하는 근거가 된다.

분리하는 시점:

| 신호 | 대응 |
|---|---|
| 배치가 도는 동안 API 응답이 눈에 띄게 느려짐 | 배치만 별도 프로그램으로 떼어 같은 서버나 다른 서버에서 실행 |
| API 서버를 2대 이상으로 늘림 | 같은 배치가 서버마다 중복 실행되지 않게 실행 잠금 추가 (예: ShedLock) 또는 배치 분리 |
| 다운로드 속도 제한 때문에 수집이 계속 밀림 | 분리로는 해결 안 됨. 하루 수집 기종 수·기종당 장수 조정. 위키미디어 규칙보다 빠르게 요청하지 않는다 |

### 3.8 규모 확장 체크리스트

MVP는 단순하게 만들고, 사용자가 많아지면 **반드시** 아래를 바꾼다. 운영 중 이 신호가 보이면 이 표부터 확인한다.

| 신호 | 반드시 바꿀 것 | 상세 |
|---|---|---|
| 조회수 UPDATE가 DB에 부담이 됨 | 조회수를 메모리에 모았다가 몇 분마다 한 번에 반영 | ERD.md 5.1 |
| 조회수를 인기 순위에 쓰기 시작함 | 같은 사람의 반복 조회(새로고침)를 세지 않게 막기 | ERD.md 5.1 |
| 배치가 도는 동안 API가 느려짐 | 배치를 별도 프로그램으로 분리 | 3.7 |
| 서버 1대로 감당이 안 돼 API 서버를 2대 이상으로 늘림 | ① 로드밸런서 추가 (Lightsail 로드밸런서, 월 약 $18) ② 배치 중복 실행 막기 (실행 잠금 또는 배치 분리) ③ 3.9 표에서 "늘릴 때 할 일"이 있는 항목 확인 | 3.7, 3.9 |
| 서버가 느려짐 (CPU·메모리 부족) | Lightsail 상위 플랜으로 변경 | 7장 |
| 기종이 많아져 검색이 느려짐 | 별칭 검색에 pg_trgm 인덱스 추가 | ERD.md 3.3 |

### 3.9 서버를 여러 대로 늘릴 수 있게 하는 원칙

MVP는 서버 1대지만, 나중에 2대 이상으로 늘릴 때 큰 공사가 없도록 처음부터 지킨다.

```
지금:   사용자 ──▶ 서버 1대 ──▶ DB

나중:   사용자 ──▶ 로드밸런서 ──┬─▶ 서버 1 ──┐
                              └─▶ 서버 2 ──┴─▶ DB (같은 DB 하나)
```

**원칙: 서버 메모리에 "기억해야 하는 것"을 두지 않는다.** 요청이 어느 서버로 가도 결과가 같아야 한다. 사용자 정보, 세션, 사진, 횟수처럼 계속 남아야 하는 값은 DB나 R2에 둔다.

| 항목 | 저장 위치 | 서버를 늘리면 | 늘릴 때 할 일 |
|---|---|---|---|
| 로그인 세션 | DB (Spring Session JDBC) | 어느 서버든 같은 세션을 봐서 로그인 유지됨 | 없음 |
| 업로드 사진 | R2 | 어느 서버가 받아도 같은 곳에 저장됨 | 없음 |
| 업로드 횟수 제한 | **DB** (최근 1시간 업로드 수를 조회) | 서버가 몇 대든 같은 기준으로 셈 | 없음. 메모리에서 세면 서버마다 따로 세어 제한이 느슨해지므로 처음부터 DB로 센다 |
| 배치 (`@Scheduled`) | 서버마다 실행됨 | **같은 배치가 서버 수만큼 중복 실행됨** | 실행 잠금(ShedLock) 또는 배치 분리 (3.7) |
| 인기 순위 캐시 | 서버 메모리 | 서버마다 따로 캐시 | 없음. 하루 한 번 바뀌는 값이라 서버끼리 잠깐 달라도 문제없음 |
| 조회수 (나중에 모아서 반영할 경우) | 서버 메모리에 모았다가 DB에 더함 | 서버마다 따로 모아 각자 더함 | 없음. 더하기라서 합쳐도 결과가 같음 |
| 업로드 중 임시 파일 | 서버 디스크 | 요청 하나 안에서 쓰고 지우므로 상관없음 | 없음. 요청이 끝나면 반드시 지운다 |

새 기능을 만들 때 서버 메모리에 값을 저장하려고 하면, 이 표에 추가하고 서버가 2대일 때도 맞게 동작하는지 먼저 확인한다.

### 업로드 보안

> 보안 항목 전체는 [SECURITY.md](./SECURITY.md)에 체크리스트로 정리했다.

- 파일 크기 제한 (예: 20MB)
- 확장자가 아니라 **파일 내용으로 이미지인지 확인**
- **픽셀 수 제한 (이미지 폭탄 방지)**: 이미지를 메모리에 올리기 전에 헤더에서 가로·세로를 먼저 읽고, 4,000만 픽셀(40MP)을 넘으면 거부한다. 동시에 처리하는 업로드 수도 제한한다.
- 사용자별 업로드 횟수 제한 (도배 방지). **DB에서 센다**: 그 사용자가 최근 1시간 동안 올린 작례 수를 조회한다. 삭제한 작례도 센다. (올렸다 지우기를 반복하는 도배를 막기 위해) 서버 메모리에서 세지 않는 이유는 3.9 참고
- 저장 파일명은 서버에서 새로 만든다. 사용자가 보낸 파일명은 쓰지 않는다.
