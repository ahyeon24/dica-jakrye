## 1. 인기 기종 ("요즘 뜨는 디카")

### 1.1 MVP에서 뺀 이유

네이버 데이터랩 검색어 트렌드로 기종별 "검색 관심도 순위"를 만들 계획이었지만, 2026-11-17 검증(`poc/datalab_poc.py`, `poc/datalab_experiment.py`)에서 **기종 단위 검색량이 너무 적게** 나왔다.

| 실험 | 결과 |
|---|---|
| 기준 "디카"와 비교, 일 단위, 기종 8개 | 기종 값이 0.00~0.20 ("디카"=100 기준). 56일 중 값이 있는 날 0~4일 |
| 기종끼리만 비교, 주 단위 | 8주 중 값이 있는 주 0~4주. 75, 100처럼 딱 떨어지는 값만 나와 실제 검색이 몇 건 수준으로 보임 |
| 작은 기준 "빈티지 디카"와 비교, 주 단위 | 마찬가지로 대부분 0 |
| 시리즈 단위 + 기준 "디카", 일 단위 | 56일 중 값 있는 날: 익서스/IXY 50일, 쿨픽스 37일, 사이버샷 8일, 케녹스/블루 4일 |

데이터랩은 검색량이 아주 적으면 값을 주지 않는 것으로 보인다. 기준 키워드를 바꿔도 해결되지 않는다. 이대로 증가율 순위를 만들면 우연히 몇 번 검색된 기종이 1위가 되는 의미 없는 순위가 된다.

### 1.2 다시 만들 때의 선택지

| 방식 | 내용 | 메모 |
|---|---|---|
| **사이트 데이터 기반 (추천)** | 우리 사이트의 업로드·조회 수로 "요즘 많이 보는 기종" 순위 | 사용자가 쌓인 뒤 가능. 조회수를 순위에 쓰면 반복 조회 막기가 필요 (ERD.md 5.1, ARCHITECTURE.md 3.8) |
| 큐레이션 | 커뮤니티·인스타 조사로 직접 고른 "인기 기종" 목록 | 출시 직후에도 가능. 화면에 "직접 고른 목록"이라고 표시 |
| 시리즈 단위 데이터랩 | "요즘 뜨는 시리즈" 또는 시리즈별 관심도 그래프 | 꾸준히 잡히는 시리즈가 2~3개뿐이라 순위보다는 그래프에 적합 |

### 1.3 원래 기능 설계 (PRD F1에서 옮김)

#### 원래 PRD F1. 요즘 뜨는 디카

- 홈에서 "최근 4주 동안 검색이 많이 늘어난 기종" 순위를 보여준다.
  - **기간**: 어제까지 최근 28일과 그 전 28일을 비교한다. 28일(4주)로 해서 요일 구성을 맞추고, 매달 초에 데이터가 적어 순위가 흔들리는 문제를 피한다.
  - 7일은 반응이 빠르지만 빈티지 디카는 기종별 검색량이 적어 순위가 매일 크게 흔들리므로 쓰지 않는다. 출시 후 실제 검색량을 보고 14일이나 7일로 줄일지 다시 판단한다. (기간은 설정값)
  - **순위 기준**: 증가율(최근 28일 ÷ 그 전 28일). 검색량이 아주 적은 기종이 우연히 몇 번 검색돼 1위가 되는 일을 막기 위해, 최근 28일 관심도가 최소 기준 미만이면 순위에서 뺀다.
  - 화면 표시 예: "최근 4주 검색 관심도 · 11월 16일 기준"
- 데이터는 네이버 데이터랩 검색어 트렌드 API로 기종명 검색 추이를 가져와 만든다. (2026년 7월부터 네이버 클라우드 플랫폼의 NAVER API HUB에서 발급. 월 30,000건까지 무료)
  - 데이터랩은 실제 검색 횟수가 아니라 상대 비율만 주므로, 화면에는 **"검색 관심도 순위"**로 표시한다. "판매 순위"라고 쓰지 않는다.
  - 한 번 요청에 키워드 그룹이 5개까지이고 값이 요청마다 0~100으로 따로 환산된다. 30개 기종을 한 순위로 묶기 위해 모든 요청에 **공통 기준 키워드**를 넣고, 그 키워드 값으로 나눠 환산한다.
  - 하루 한 번 배치로 갱신하고 결과는 캐시한다.
- 사용자가 쌓이면 우리 사이트의 업로드·조회 수 기반 순위로 바꾼다. (MVP 이후)


### 1.4 원래 배치 설계와 데이터랩 API 정보 (ARCHITECTURE 3.5에서 옮김)

#### 원래 ARCHITECTURE 3.5 인기 기종 배치 (네이버 데이터랩)

> 네이버 개발자센터(developers.naver.com)는 2026년 7월 말부터 데이터랩 API 신규 신청을 받지 않는다. **네이버 클라우드 플랫폼(NCP)의 NAVER API HUB**에서 발급받는다. 예전 개발자센터의 주소·헤더·키는 쓸 수 없으므로, 인터넷의 예전 예제 코드를 그대로 따라 하지 않는다. (2026-11-17 확인)

**API 정보** ([NCP 검색어 트렌드 API 문서](https://api.ncloud-docs.com/docs/naver-api-hub-search-trend))

| 항목 | 내용 |
|---|---|
| 주소 | `POST https://naverapihub.apigw.ntruss.com/search-trend/v1/search` |
| 인증 헤더 | `X-NCP-APIGW-API-KEY-ID: {Client ID}`, `X-NCP-APIGW-API-KEY: {Client Secret}` |
| 요청 본문 | `startDate`, `endDate`(yyyy-mm-dd, 2016-01-01부터), `timeUnit`(date/week/month), `keywordGroups`(`groupName` + `keywords`) |
| 키워드 그룹 | 요청당 최대 5개 |
| 그룹당 키워드 | 문서에 20개와 5개가 함께 적혀 있어 **5개 이하**로 쓴다 |
| 결과 | 기간별 `ratio`. 요청 전체에서 가장 큰 값을 100으로 둔 상대값 (예시에서 두 번째 그룹 최고값이 약 30 → 그룹별이 아니라 요청 전체 기준) |
| 한도 | **월** 최대 50,000건 (30,000건까지 기본 무료, 그 이상은 지금만 한시적 무료). 차면 자동 차단. 키당 초당 50회 |
| 우리 설정 | 콘솔에서 월 한도 **5,000건**, 80%에서 이메일 알림 |

콘솔 한도는 적용까지 수초 걸려 초과 호출이 생길 수 있고 일 한도 설정이 없다. 그래서 **우리 배치에서도 하루 호출 수를 직접 센다.** (하루 50회를 넘으면 그날은 멈추고 오류 로그를 남김)

**처리 순서**

1. 하루 한 번 실행한다.
2. **기간**: 어제까지 최근 56일을 하루 단위(`timeUnit=date`)로 **한 번에** 요청한다.
   - 데이터랩은 요청한 기간 전체에서 가장 큰 값을 100으로 맞추므로, 두 기간을 따로 요청하면 서로 비교할 수 없다.
   - 받은 값을 앞 28일(비교 기간)과 뒤 28일(최근 기간)로 나눠 각각 합산한다.
   - 기간 길이(28일)는 설정값으로 둔다. 데이터랩에서 과거 데이터를 언제든 다시 받을 수 있으므로, 기간을 바꿔도 별도 데이터 이전이 필요 없다.
3. 기종을 4개씩 나누고, 모든 요청에 **공통 기준 키워드** 1개를 넣는다. (요청당 키워드 그룹 최대 5개)
   - 기준 키워드는 모든 기종보다 검색량이 많은 단어로 고른다. (예: "디카")
   - 기종 하나의 그룹에는 `camera_alias.use_for_trend`가 켜진 별칭을 **최대 5개**까지 넣는다. (예: "익서스 30", "IXUS 30")
   - 기종 30개면 하루 8회, 500개면 하루 125회(월 약 3,750회) 호출한다.
4. 각 기종 값을 같은 요청의 기준 키워드 값으로 나눠 환산한다.
5. 순위:
   - 최근 28일 관심도가 **최소 기준 미만**인 기종은 제외한다. (기준값은 설정값, 출시 후 실제 분포를 보고 정함)
   - 남은 기종을 **증가율**(최근 28일 ÷ 그 전 28일) 순으로 정렬한다. 증가율이 같으면 최근 28일 관심도가 높은 순.
   - 그 전 28일 값이 0이면 증가율 없이 "NEW"로 표시하고 관심도 순으로 뒤에 붙인다.
6. 결과를 `trend_snapshot`에 저장하고 캐시한다.
